# ADR-0030 — The RFP Orchestrator is a GitHub Copilot-harness agent with four workflow tools and two hooks

- **Status:** Accepted
- **Date:** 2026-10-31
- **Deciders:** Solution architecture, with the user's approval in the Slice 7 plan (agent plus hooks)
- **Related:** [ADR-0001](0001-deterministic-workflow-spine-agents-at-the-leaves.md), [ADR-0012](0012-harness-selection-github-copilot-harness.md), [ADR-0015](0015-leaf-steps-are-prompts-called-by-agent-flows.md), [ADR-0026](0026-failure-handling-and-stage-reruns.md), ARCHITECTURE.md §3.3, §10.1-10.3

## Context

ADR-0015 made every pipeline step a prompt called from a flow and deferred the one conversational agent, the
`RFP Orchestrator`, to Slice 7. ARCHITECTURE.md §3.3 gives it four jobs: run status, explaining a flag, rerunning
a stage, and answering "why did we answer CV-013 this way". §10.2 designs hooks around it:

- Pre tool use denies an unsafe call.
- Post tool use writes the audit record.
- After tool failure classifies failures.

**Platform facts (checked 2026-10-31):**

| Fact | Source |
|---|---|
| Hooks exist only for agents on the GitHub Copilot harness | [hooks](https://learn.microsoft.com/en-us/microsoft-copilot-studio/agents-experience/hooks-overview) |
| Hooks are attached per agent from the command bar's … → Hooks | same |
| Only Pre tool use can block, by returning `permissionDecision = deny` | same |
| Hooks fail open | same |
| The three tool events need at least one tool on the agent | same |
| A tool workflow must respond within 100 seconds | [agent flows as tools](https://learn.microsoft.com/en-us/microsoft-copilot-studio/flow-agent) |
| Skills and memory are GitHub Copilot harness only | [harnesses](https://learn.microsoft.com/en-us/microsoft-copilot-studio/harnesses-overview) |

**Spike M0.1:**
- `pac copilot init --authoring-mode cli-copilot --environment <dev>` created the agent (schema name
  `hrs_RFPOrchestrator`, model Claude Sonnet 4.6).
- In the portal it shows the new agent experience: Skills, Tools, Knowledge, Connected agents and Memory. That
  identifies it as a GitHub Copilot-harness agent.
- The Hooks dialog is available in the dev tenant.

## Decision

**The agent.**
- `RFP Orchestrator` on the GitHub Copilot harness, published to Teams for the pilot recipient.
- Its instructions are short: the four tools, the one-letter RFP keys, and never stating a company fact the tools
  didn't return.
- It has no knowledge source, so it has no route to gold data (§10.3, ADR-0007).

**Four tools.** Each is an agent flow with *When an agent calls the flow* and *Respond to the agent*, generated by
`tools/flowgen/build.py`. Each lists rows and gets its text from `rfp_tools/orchestrator.py`.

| Tool | Answers |
|---|---|
| `RFP - Get Run Status` | Status, last completed stage, open waits (SME gaps, OCR verifications, pending approval), the last 8 run-log rows with credits |
| `RFP - Explain Flag` | Each flag on a requirement: type, severity, rule and approved position, reason, who resolved it |
| `RFP - Explain Answer` | Compliance value, the approved answer ID and its question (hard rule 5), response code and text, or the gap and SME answer |
| `RFP - Rerun Stage` | Reruns from stage N with ADR-0026's undo rule |

How `RFP - Rerun Stage` runs:
1. `rerun_check` refuses the call when:
   - the pipeline is Running
   - the RFP is Completed (filed)
   - N is outside 1-9
   - N is beyond the stage the RFP has reached
2. A rerun of stage 3 runs from stage 2.
3. It responds first, then removes rows and restarts, so a slow delete can't exceed the 100-second limit.
4. It writes a run-log row "Rerun from stage N (RFP Orchestrator)".

**Two hooks.**
- **Pre tool use**, scoped to `RFP - Rerun Stage`: denies the call when the RFP is Running or Completed, or the
  stage is out of range. It repeats `rerun_check`. Nothing depends on it, because the tool refuses on its own;
  this is §10.2's defense in depth.
- **Post tool use**, all tools: writes an audit row to `hrs_runlog` with the tool, its parameters, the user's
  Entra object ID and the conversation ID.
- **After tool failure is dropped.** The tools return their own errors as text, and Learn shows the hook can only
  add context. §10.1's "Tool calls audited" row is covered by Post tool use.
- The hook workflows start from the portal's starter workflow for each event, so the field names match what
  Copilot Studio checks. Their logic then moves to flowgen, like every other flow.

## Consequences

- The design's last agent exists. A2's open question (the `bots/` and `botcomponents/` source layout) is answered
  by unpacking it into `solution/src` (recorded in ARCHITECTURE.md §12.2).
- Conversations bill at the GitHub Copilot harness's usage rates
  ([billing](https://learn.microsoft.com/en-us/microsoft-copilot-studio/agents-experience/billing-credit-overview)).
  The pipeline's cost is unchanged.
- Hooks are preview and fail open (Q2 accepted that). No closed control in §10.1 depends on them.
- **[UNVERIFIED]** how a CLI-authored agent's tools and hooks round-trip through `pac copilot pull` and solution
  export. Checked when the agent is synced into `solution/src`.
